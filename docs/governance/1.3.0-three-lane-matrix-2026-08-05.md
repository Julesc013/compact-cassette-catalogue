# C3 1.3.0 three-lane stable matrix decision

Decision date: 5 August 2026

Status: ratified owner decision; authoritative for Beta 1 and stable

This decision supersedes the four-lane release plan recorded at the immutable
`v1.3.0a1` checkpoint. The Alpha result remains truthful historical evidence:
Alpha compiled four diagnostic x86/x64 lanes. The Alpha tag is not moved or
rewritten. From this decision forward, C3 1.3.0 has exactly three public release lanes.

## Release doctrine

> **C3 1.3.0 is the final stable original VB.NET WinForms release, built from
> one source-identical project into three portable classic executable packages:
> x86/net40 using Visual Studio 2017 for Windows XP SP3, x64/net48 using Visual
> Studio 2022 for Windows 7 SP1, and native ARM64/net481 using Visual Studio 2026
> for Windows 11 RTM. Installers are outside the legacy core release and may
> later be supplied as a separately qualified Universal Setup product binding.**

| Release lane | Authoritative compiler at freeze | Framework | Minimum C3 execution target |
| --- | --- | --- | --- |
| `win-x86-net40` | Visual Studio 2017, latest 15.9 servicing release | .NET Framework 4.0 Full | Windows XP SP3 x86 |
| `win-x64-net48` | Visual Studio 2022, latest 17.14 servicing release | .NET Framework 4.8 | Windows 7 SP1 x64 |
| `win-arm64-net481` | Visual Studio 2026, latest stable servicing release | .NET Framework 4.8.1 | Windows 11 21H2/RTM ARM64 |

The initial servicing pins recorded on the decision date are VS2017 15.9.81,
VS2022 17.14.36, and VS2026 18.8.2. They are starting pins, not an evergreen
build policy. Immediately before candidate freeze, each builder is updated to
the latest stable servicing release in its declared family. That exact
installation is then locked for candidate, qualification, reproducibility, and
final stable builds.

VS2015/MSBuild 14 remains the historical compiler oracle for reproducing and
comparing the official C3 1.2.0 Beta 1 binaries. It is not a C3 1.3 release
compiler. The permanent distinction is:

```text
VS2015/MSBuild 14 = historical 1.2 reconstruction oracle
VS2017/MSBuild 15 = authoritative 1.3 x86/net40 compiler
```

The removed `win-x64-net40` profile remains useful only in the compatibility
laboratory for the official 1.2 x64/net40 artifact. It is not rebuilt or
published as C3 1.3. The removed `win-x64-net481` lane has no release role:
x64 systems use `win-x64-net48`; net481 exists specifically for native ARM64.

## Build and target proof

Builder hosts and minimum execution targets are separate. VS2017 and VS2022
run on maintained builder hosts and cross-target XP and Windows 7 respectively.
VS2026 runs on a supported Windows 11 builder. Runtime claims are established
only on the exact target environments, not by running old Visual Studio versions
on old operating systems.

Every candidate lane records:

```text
Visual Studio product version and build
MSBuild executable version and SHA-256
actual vbc compiler path, version, and SHA-256
.NET Framework reference-assembly path and hashes
Windows SDK/resource tool version, where used
build-host OS identity
source commit
effective MSBuild tools version
external toolchain-lock SHA-256
```

The old-style project keeps `ToolsVersion="14.0"` as genetic metadata. Each
release build overrides the effective tools version, disables shared
compilation, writes an MSBuild binary log, and verifies the actual compiler and
reference assemblies. The actual `ResGen.exe` is forced by full path, hashed,
and retained with property/binary-log evidence. Release qualification rejects a
different Visual Studio family, a servicing version below the decision-date
floor, or an unlocked input.

The candidate lock is external to source and immutable. It binds clean source
commit `C` to the exact expected remote ref and exact tool/input hashes; its own
SHA-256 is retained in build/package evidence. A tracked lock cannot contain its
own resulting commit identity and is therefore a repository template only.
Candidate mode rejects any dirty file, submodule drift, remote mismatch, lock
change, or non-rebuild invocation before compilation is trusted.

Hosted status contexts and generic CI runners are supplemental static feedback,
not release authority. Unless a later owner decision explicitly adopts a
specific hosted environment, only retained evidence from the pinned maintained
builders and exact target machines can satisfy candidate, reproducibility, or
runtime qualification gates. The absence of a GitHub status context neither
creates a PASS nor invalidates otherwise complete retained machine evidence.

The binary contract is closed rather than inferred from lane labels:

| Lane | PE machine | Header | CorFlags | Framework |
| --- | --- | --- | --- | --- |
| `win-x86-net40` | `0x014c` / I386 | PE32 | ILONLY + 32BITREQ | `.NETFramework,Version=v4.0` |
| `win-x64-net48` | `0x8664` / AMD64 | PE32+ | ILONLY, not 32BITREQ | `.NETFramework,Version=v4.8` |
| `win-arm64-net481` | `0xaa64` / ARM64 | PE32+ | ILONLY, not 32BITREQ | `.NETFramework,Version=v4.8.1` |

ARM64 is a new release-blocking boundary. It requires an explicit ARM64 project
configuration and proof of native `AA64` output on an actual Windows-on-ARM
device or VM. AnyCPU, x64 emulation, ARM64EC, or a relabelled x64 executable is
not acceptable.

Builder verification compiles, inspects, and packages. Target-machine
verification transfers the exact retained package and its authenticated
five-entry manifest, checks the ZIP and every extracted file by SHA-256, derives
the actual OS/service-pack/architecture/Full-Framework identity, launches it,
performs the workflow matrix, and retains evidence. Target tooling must execute
under Windows PowerShell 2 for the XP lane. A cross-built ARM64 binary is never
treated as runtime-qualified by an x64 builder.

## Portable distribution contract

The only authoritative stable assets are:

```text
C3-v1.3.0-win-x86-net40-portable.zip
C3-v1.3.0-win-x64-net48-portable.zip
C3-v1.3.0-win-arm64-net481-portable.zip
SHA256SUMS.txt
```

Each ZIP contains only the allow-listed classic WinForms executable, its
matching `.exe.config`, and release text/evidence files. No raw EXE is an
authoritative download. C3 itself requires no installation or administrator
rights for ordinary use. The ARM64 operating-system prerequisite is a separately
installed .NET Framework 4.8.1 runtime on Windows 11 RTM.

C3 1.3 excludes MSI, MSIX, ClickOnce publication, bootstrapper, installer,
uninstaller, service, scheduled task, background updater, self-contained
runtime, and new application DLL graph. Old ClickOnce/bootstrapper metadata may
remain inert for source identity, but package verification must prove none of
its outputs entered a release ZIP. Historical installer projects remain archive
evidence and are excluded from the build, validation, and download graph.

Universal Setup is a later independent distribution programme. It may consume
the already-qualified C3 ZIP bytes by exact SHA-256 through a separately pinned
provider and product recipe. It must not rebuild, rename, modify, or independently
enumerate the C3 payload; change the catalogue format; become required for
portable use; or delay/redefine C3 1.3 stable.

## Qualification minimums

- `win-x86-net40`: Windows XP SP3 x86 with .NET Framework 4.0 Full, plus a
  separately recorded final 4.0.3 update state.
- `win-x64-net48`: fully serviced Windows 7 SP1 x64 with .NET Framework 4.8,
  described as directly tested C3 compatibility rather than current Microsoft
  support, plus representative later x64 Windows smoke tests.
- `win-arm64-net481`: Windows 11 21H2/RTM ARM64 with separately installed .NET
  Framework 4.8.1, native-process proof, complete workflows, rendering/DPI
  checks, cross-lane XML identity, and reverse opening by C3 1.2.0 Beta 1.

All lanes must prove matching runtime configuration, settings-schema parity,
zero runtime DLL payload, offline/blocked-network safety, and complete
New/Open/Edit/Save/Save As/Close/list/filter/settings workflows.
