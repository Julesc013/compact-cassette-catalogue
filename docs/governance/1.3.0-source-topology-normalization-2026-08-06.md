# C3 1.3.0 source-topology normalization decision

Date: 6 August 2026

Status: implemented and mechanically verified

## Decision

C3 1.x uses the **original-simple** production topology. It does not partially
adopt the modular `dev/2.x` `src/` structure.

After normalization, the only production-source roots are:

```text
Compact Cassette Catalogue/
Compact Cassette Catalogue Installer/
Compact Cassette Catalogue Uninstaller/
```

Repository infrastructure remains outside those roots by role:

```text
build/       build, package, and release controls
tests/       characterization and adversarial tests
fixtures/    immutable test inputs
spec/        catalogue and compatibility specifications
docs/        governance, plans, and qualification contracts
release/     release metadata and validation records
Resources/   repository documentation/branding assets, not compiled source
```

There is no production `src/` directory or root-level `SetupShared/`
production-source directory on `dev/1.x` after the normalization.

## What the current directories mean

The `src/` directory observed after consolidating worktrees was not tracked by
`dev/1.x`. It was ignored `bin/obj` residue from the previous `dev/2.x`
checkout in the same physical directory. It contained no authoritative 1.x
source and was removed with a scoped `git clean -fdx -- src/` after an exact
dry run.

The former `SetupShared/` was different. It contained 13 production VB.NET files introduced
during the Alpha 3 classic-setup repair. Both old-style setup projects link
those exact files directly, as does the setup characterization project. This
keeps one implementation and adds no runtime DLL, but its root-level location
creates an undesirable hybrid between the original three-project tree and the
modular 2.x layout.

## Canonical setup ownership

Move the one canonical shared setup implementation, without editing its
contents, to:

```text
Compact Cassette Catalogue Installer/Shared/
```

The installer owns the common install/remove transaction engine because it
owns bundle verification, install, repair, upgrade, and installed-state
creation. The uninstaller continues compiling the same physical files through
old-style linked `Compile` items. The test project links the same canonical
files.

Do not duplicate shared files into both projects, create a setup DLL, create a
fourth production project, or place legacy setup source under root `src/`.

## Mechanical implementation transaction

The focused topology transaction:

1. record SHA-256 for every current `SetupShared/*.vb` file;
2. `git mv` the files to the Installer `Shared/` directory;
3. update installer, uninstaller, and setup-test project includes and logical
   `<Link>` paths;
4. update build validators and documentation that name `SetupShared`;
5. assert the same 13 source files are compiled once into each setup EXE and
   the characterization project;
6. assert source bytes are unchanged across the move;
7. prove root `SetupShared/` and `src/` are absent on `dev/1.x`;
8. run setup genome, offline, journal, package, and complete source gates; and
9. records any binary difference as path/build metadata rather than claiming
   byte identity without proof.

## Implementation result

The 13 files were moved with `git mv` and no content edit. Their accepted names
and pre-move SHA-256 values are frozen in
`build/setup-shared-source-contract.json`. The Installer compiles them from its
local `Shared/` directory; the Uninstaller and setup characterization project
link the same resolved physical files using the same logical `Shared/` names.

`build/validate-1x-source-topology.ps1` now fails closed on an unexpected file,
hash change, consumer include/link mismatch, duplicate physical source,
production VB file outside the three product roots/tests, or return of root
`src/`/`SetupShared/`. The complete preparation gate invokes this contract
before any build or release evidence may pass.

The topology, setup-offline, durable-journal, setup-genome, and complete
source/characterization gates passed after the move. No application form,
catalogue, setup-engine logic, release identity, package, tag, feed, or branch
authority changed in this transaction.

No application form or layout file changes in the topology commit. Alpha 5
layout work begins only after this normalization passes.

## Genome and release consequences

The move is a reviewed production-path change, not a new source/type/control or
runtime-assembly change. Update the narrow production-path/setup-genome
allow-list only for the exact old-to-new mapping. Do not regenerate either
baseline.

The move invalidates old build evidence by design. Alpha 4 remains immutable;
Alpha 5 rebuilds every application/setup executable and package after topology
and layout work are complete. `master`, `legacy/1.x`, `dev/2.x`, tags, feeds,
and public release surfaces do not move during normalization.

The later Alpha 5 release-identity projection changes only the closed
`SetupBundleRuntime.vb` payload stage/label literals. The shared-source
contract advances that one reviewed hash while retaining the same 13-file set,
canonical physical root, and three project consumers; the other 12 hashes
remain frozen at their topology-normalization bytes.

## Why not move all 1.x projects into `src/`

A full 2.x-style relocation would change solution/project paths, old Designer
assumptions, scripts, fixtures, genome surfaces, historical comparisons, and
release evidence without improving the 1.3 user experience. That architecture
already belongs to `dev/2.x`.

The final legacy release benefits from the opposite choice: keep its original
project directories obvious, keep one physical setup implementation, and
remove the one root-level production-source exception.
