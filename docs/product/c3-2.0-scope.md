# C3 2.0 product scope

Status: **Accepted programme scope; individual designs remain gated**

This document owns the product requirements for C3 2.0. The
[execution plan](../planning/2.0-execution-plan.md) owns sequence and status;
`ROADMAP.md` is the short public milestone index. Issues may divide work but may
not silently redefine this scope.

## Required for 2.0 stable

### Compatibility and governance

- Independent product, assembly, catalogue-format, and update-channel versions.
- An immutable inventory of public 1.x releases and every catalogue variant they
  actually emitted.
- Executable old-reader/new-writer and new-reader/old-writer compatibility
  evidence for the supported legacy profile.
- One-time, idempotent migration of supported 1.x user preferences.
- Separate stable, preview, and legacy-maintenance update channels.
- Side-by-side-safe product, settings, and future setup identities.

### Catalogue and persistence

- One native-superset logical catalogue with explicit relationships, atomic
  transactions, immutable version-bound reads, and no profile syntax or active
  `DataSet` in its ordinary API.
- Whole-document legacy/native adapter convergence before canonical mutation
  becomes production authority; partial synchronized document truths are
  prohibited.
- Durable opaque identities where the active profile can preserve them, honest
  session-scoped legacy identity otherwise, and distinct document session,
  catalogue, content-version, semantic-state, disk-revision, and destination-
  lease concepts.
- Command/draft/result mutations with validation, clocks, ID generation,
  savepoints, history, and recovery outside forms.
- Explicit logical validity, current-profile direct-save validity, and requested
  export-profile representability.
- A deterministic, documented native v2 XML profile only after the domain model
  and migration cases are proven.
- An explicit legacy mode that preserves v1.1 semantics.
- Conversion to a new copy; originals are never silently replaced.
- Loss-aware v2-to-v1.1 export with a preview and machine-readable report.
- Transactional load/save, backup and recovery, external-edit protection, and a
  crash-recovery journal appropriate to the final workspace model.
- Deterministic normalization and serialization across supported cultures.
- Accepted semantics for partial/historical dates, uncertainty, provenance,
  units, vocabularies, stored text, comparison/search keys, and native-profile
  succession without rewriting the frozen Alpha 4 profile.

### Application behavior

- One net40-compatible document lifecycle and operation coordinator shared by
  Desktop and CLI, with toolkit-neutral immutable events and allowed actions.
- Monotonic optimistic concurrency, semantic fingerprints, bounded snapshot
  leases, version-bound cursor queries, and atomic version-bound operation plans.
- Snapshot-based saves in which failure leaves active state unchanged and saving
  version N cannot mark a newer version N+1 clean.
- Explicit external-conflict actions and separate undo history, workspace
  recovery, migration journals, verified backups, and conflict copies.
- Stable machine result/operation codes with localizable resource keys and no
  final English prose or raw exception text in application contracts.
- Typed prerequisite requirements, suggested actions, continuations,
  create-and-select results, and version-bound compound plans so one user goal
  commits atomically and cancellation leaves no partial reference data.

### Desktop experience

- A coherent native WinForms workspace with navigation, list, inspector/editor,
  status, and command surfaces.
- Reusable editor patterns, inline validation, useful empty states, keyboard
  access, assistive-technology names, system contrast support, and tested DPI
  behavior.
- Explicit dirty, compatibility, migration, filter, and recovery state.
- Practical undo/redo for catalogue mutations and previews for destructive or
  bulk operations.
- A goal-first blank-catalogue path from Add Tape through any required Model and
  Brand creation with preserved drafts, automatic return/selection, no expected-
  prerequisite error dialog, and one compound undo entry.
- No storage-table or XML knowledge in forms.
- One shared C# 7.3/net40 presentation path across both lanes; net48-only runtime
  behavior remains at the x64 host boundary.

### Quality and delivery

- A bounded Application-backed `c3.exe` supporting inspect, validate, migration
  dry-run/commit, recovery, and loss-aware legacy export with deterministic,
  schema-versioned machine output and preserved process compatibility. Rich
  catalogue mutation can follow later.
- Both portable build lanes produced from one source identity and staged payload
  contract.
- One authoritative manifest-derived, version-rooted portable payload per lane;
  no loose executable or alternate package owner.
- Reproducible packaging, SHA-256 manifests, binary identity checks, security
  fixtures, performance budgets, accessibility checks, and recorded minimum-OS
  evidence.
- User migration, recovery, backup, and rollback guidance.

## Desired when evidence and schedule allow

- Complete C# 7.3 managed production sources, including the replacement shell.
  C# is the target end state, but removal of proven VB code is not more important
  than compatibility or release safety.
- Multiple open catalogues after session and command ownership are proven for one
  document.
- Saved views, column layouts, and import/export profiles.
- A privacy-reviewed support bundle with explicit user review and consent.
- A Universal Setup binding that installs exactly the verified portable payload.
- A line-mode or full-screen TUI only if it is independently complete and
  qualified; otherwise its executable/capability is explicitly deferred.

These items may enter 2.0 only through their own acceptance criteria. A partial,
unproven version does not remain merely to satisfy a checklist.

## Forward-compatible model seams, deferred experiences

The v2 model and format may reserve documented extension envelopes and stable
references for these capabilities, but their full user experiences are planned
after 2.0 unless separately accepted:

- embedded media and J-card assets;
- arbitrary custom-field editing;
- catalogue merge and conflict-resolution UI;
- rich CLI query, report, and batch automation;
- automatic three-way catalogue merge;
- reference-data marketplaces or automatic enrichment;
- an out-of-process executable extension SDK; and
- alternate native shells.

## Explicit 2.0 non-goals

- Automatic self-update.
- HTTP downgrade or disabled certificate validation.
- A second implementation of catalogue rules for either build lane.
- C or C++ implementations of catalogue/domain behavior.
- In-process third-party plugins.
- A setup-only distribution with no portable fallback.
- ARM64, mobile, web, cloud sync, accounts, or hosted storage.
- MSI, MSIX, ClickOnce, web-installer, or setup-only payload ownership.
- Silent conversion of a 1.x catalogue into a v2 catalogue.
- An identity sidecar or private C3 elements added to strict legacy XML.
- A half-qualified TUI, arbitrary query language, or frontend-specific catalogue
  mutation owner.

## Stable exit criteria

C3 2.0 can be called stable only when all required scope has either passed its
recorded gate or been explicitly removed from the stable contract before release.
At minimum, there must be no open data-loss or corruption defect; the complete
1.x compatibility matrix must pass; settings migration and rollback must pass;
both build lanes and the validator/migrator must agree; manual OEM+, accessibility,
DPI, and minimum-OS matrices must be recorded; and downloaded release artifacts
must match the promoted hashes.
