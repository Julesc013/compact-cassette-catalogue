# C3 1.3.0 Alpha 5 layout qualification specification

This specification replaces the Alpha 4 property-only layout characterization.
A form is not safe merely because it is sizable, maximizable, font-scaled, or
scrollable.

## Process model

Run each scale/matrix cell in a new Windows STA process. The child process:

1. creates the form and representative state;
2. calls `Show` and creates native handles;
3. processes the message queue;
4. applies the requested bounds and font-relative scaling;
5. calls `PerformLayout` and processes messages again;
6. captures geometry, preferred text sizes, focus/tab/access-key state, and
   scroll ancestry;
7. runs authoritative structural assertions;
8. writes one deterministic JSON result; and
9. optionally emits a `DrawToBitmap` diagnostic image before closing.

Static WinForms and scaling state must not leak between cells.

## Matrix

Effective work areas:

```text
800 x 552
1024 x 720
1366 x 728
1920 x 1040
```

Relative font/scaling profiles:

```text
1.00
1.25
1.50
2.00
```

Content profiles:

```text
empty catalogue
ordinary populated catalogue
maximum-length representative strings
all optional editor sections enabled
long validation messages
large result set
```

Mandatory forms run every applicable profile. Conditional forms first run a
smaller characterization grid and enter reconstruction only when a defect is
reproduced.

## Geometry record

Each visible control record includes:

```text
process/form/state identity
control name and type
parent path
bounds and client/display rectangles
preferred size and measured text size
visible/enabled/tab-stop/tab-index state
dock, anchor, autosize, margin, and padding
access key and accessible name/role/state
scrollable ancestor and reachability
native handle-created state
```

The root result records source commit, test executable hash, OS/build,
architecture, font/scaling profile, work area, theme/High Contrast state,
duration, layout-event count, handle delta, memory delta, and assertion list.

## Closed structural assertions

Fail a cell for:

- unexpected intersection of visible siblings with the same parent;
- a required visible control outside a non-scrollable display rectangle;
- a required control unreachable through its scrollable ancestor;
- clipped preferred label/button/check/radio text;
- a static command outside its declared command bar;
- duplicate control names or duplicate static controls after repeated opens;
- duplicate/broken tab ordering or access keys within one scope;
- an interactive target below the approved minimum;
- a default size that immediately scrolls without a documented need;
- a larger window that exposes no additional useful content;
- reconstructed-form `AutoScroll=True`;
- right/bottom anchoring of the direct canvas in a scrollable viewport;
- known static controls created at runtime;
- fixed geometry mutation in `Load`, `Shown`, or `Resize` handlers;
- a label whose preferred/measured size exceeds its assigned area;
- an overlay pair with more than one visible member; or
- a button moving outside its semantic row/group during scaling.

The only initial overlap allow-list is the named, mutually exclusive
`pnlEmptyCatalogue`/`pnlEditorViewport` layer pair. New exceptions require a
reviewed form/name/state rule, not a type-wide tolerance.

## Source-policy authority

Scan production form handlers and geometry helpers. Prohibit:

```text
Controls.Add(New Button ...)
ClientSize =
control.Bounds =
control.Left/Top/Width/Height =
incremental Left/Top movement
```

Designer-generated assignments are expected; behaviour handlers are not. A
source-policy exception must identify a truly dynamic control and prove why it
cannot be Designer-declared.

## Accessibility authority

Automated checks cover keyboard reachability, tab order, unique access keys,
default/cancel button contracts, label targeting, accessible names, and focus
restoration state. Retain UIA/MSAA tree snapshots with name, role, state,
bounds, and focus order.

Manual authority covers:

- keyboard-only completion of every normal workflow;
- screen-reader walkthrough of main, creation, list, error, and setup flows;
- High Contrast Black and White;
- visible focus and selection when focus changes;
- error summary plus first-invalid-control focus; and
- no information communicated by colour alone.

## Native visual authority

The canonical Windows 7/96-DPI/default-size screenshot receives owner visual
approval against the immutable inheritance reference. Other native captures
prove metric and semantic fidelity at 100%, 125%, 150%, and 200%, XP/classic
font/theme, High Contrast, minimum work area, and maximum content.

`DrawToBitmap` is a diagnostic aid. It cannot substitute for native rendering,
real-DPI, keyboard, or assistive-technology evidence.

## Performance and lifecycle authority

For every major form:

- create/show/close repeatedly;
- resize rapidly through the work-area sequence;
- record total and peak `Layout` events;
- record handle and memory growth;
- reject duplicate event subscriptions or controls;
- prove resize does not reload list data;
- measure list population with and without `BeginUpdate` where relevant;
- use `SuspendLayout` only during controlled initialization; and
- enable double buffering only when measured flicker justifies it.

Set threshold baselines from Alpha 4 before choosing hard limits. Alpha 5 may
improve those limits but may not silently relax them after a regression.

## `UI-START-001` launch gate

Track the intermittent x64 process-without-window observation independently of
layout correctness. Instrument UTC/high-resolution timestamps for:

```text
process start
MyApplication startup entered/completed
frmMain constructor entered
InitializeComponent completed
Load entered/completed
handle created
Shown
first idle
```

Run repeated cold and warm launches for x86 and x64 from exact packages. Retain
process exit, exception/event-log, window-handle, timeout, and milestone data.
ARM64 runs natively on the exact target. No cleanup kill counts as a successful
launch/close. Layout work must not create a first-window latency regression or
message/layout loop.

## Evidence hierarchy

| Evidence | Authority |
| --- | --- |
| Geometry/control-tree JSON | Automated structural authority |
| Text measurement and reachability | Automated layout authority |
| Source-policy scan | Runtime-geometry/static-command authority |
| Native screenshots at real DPI | Visual-review authority |
| Keyboard/UIA/screen-reader/High Contrast runs | Accessibility authority |
| Lifecycle/startup traces | Stability authority |
| `DrawToBitmap` atlas | Diagnostic aid only |

## Result retention

Every retained result binds source commit, package/build hash where applicable,
lane, OS image/build, display/font profile, content fixture, test executable,
operator, date, expected/actual result, and evidence path. Blank, skipped, or
inaccessible rows are not passes.

The final form-by-form report records previous failure, new hierarchy, default
and maximized behaviour, complete matrix result, manual observations, and
source/tag/package hashes.
