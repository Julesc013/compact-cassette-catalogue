# C3 1.3.0 classic setup manifest contracts

Status: Alpha 5 test-distribution normative specification; the same closed
format remains planned for Beta 1 after explicit owner approval.

## Payload manifest

Every setup bundle contains one generated `payload.xml` beside `SETUP.exe` and
one closed `payload` directory. Schema version 1 has this shape:

```xml
<C3SetupPayload schemaVersion="1">
  <Product version="1.3.0" stage="Alpha 5" label="1.3.0a5"
           lane="win-x86-net40" architecture="x86" framework="v4.0"
           sourceCommit="0123456789abcdef0123456789abcdef01234567" />
  <Files>
    <File path="Compact Cassette Catalogue.exe" size="123" sha256="..." />
  </Files>
</C3SetupPayload>
```

The exact payload file set is:

```text
Compact Cassette Catalogue.exe
Compact Cassette Catalogue.exe.config
UNINSTALL.exe
UNINSTALL.exe.config
README.txt
RELEASE_NOTES.txt
BUILD.txt
```

Validation rejects unknown schema elements/attributes, missing or duplicate
entries, wrong identity/lane, case-colliding names, rooted/device/UNC paths,
empty segments, `.` or `..`, alternate data streams, directory entries,
reparse points, unsafe normalization, incorrect length/hash, unexpected files,
wrong PE/framework/config metadata, and mismatched setup/uninstaller identity.
SHA-256 text is exactly 64 lowercase hexadecimal characters.

The payload manifest is generated from the same verified application output and
package metadata used by the portable ZIP. Setup never maintains a second
independent product file list.

## Installed-state manifest

Successful setup writes `C3.installed.xml` with schema version 1. It records:

- product version, stage, label, lane, architecture, and framework;
- setup version and source commit;
- per-machine scope and canonical install root;
- each owned file path, length, and SHA-256;
- registry hive, natural architecture view, and exact uninstall key;
- each created shortcut path and target;
- payload-manifest and executing setup-EXE SHA-256;
- installation timestamp and install/repair/upgrade mode;
- prior label/source when upgraded; and
- transaction identifier and `complete` state.

The installed manifest is written first in staging and becomes authoritative
only after installed bytes, registry, and shortcuts are re-opened and verified.
The uninstaller refuses deletion when identity, containment, or ownership
validation fails.

The enclosing setup ZIP SHA-256 remains in external release evidence and
`SHA256SUMS.txt`; it cannot be embedded into its own bytes without the same
self-reference defect already prohibited for locks and tag records. Runtime
installed state therefore binds the exact executing `SETUP.exe` and payload
manifest instead. Release verification separately binds that setup executable,
manifest, and payload to the retained ZIP.

`C3.installed.xml` itself is the signed-off ownership index and therefore does
not attempt to hash itself. Its fixed name is owned by the setup protocol; the
closed `Files` collection hashes the seven installed payload files. This avoids
the same impossible self-reference class previously removed from the candidate
toolchain lock and annotated-tag record.

## Containment and ownership

Every path is canonicalized with operating-system APIs and compared using
ordinal case-insensitive Windows semantics. Owned descendants must remain below
the recorded install root after normalization and must not traverse a reparse
point. The install root itself must not be a volume root, Windows directory,
Program Files root, profile root, device path, or UNC share.

Unknown files are never overwritten or deleted silently. Catalogue XML, profile
settings, exports/logs outside the install root, and unowned content are never
removed. A non-empty directory is preserved after owned items are removed.
