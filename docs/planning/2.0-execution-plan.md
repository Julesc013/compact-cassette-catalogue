# C3 2.0 execution plan

Status: **Active**  
Programme baseline: 6 August 2026

This is the one repository-owned implementation checklist for C3 2.0. It owns
dependency order, gates, and completion state. `ROADMAP.md` summarizes public
outcomes; GitHub Issues and future AIDE work units own individual assignments.
They link here instead of copying this checklist.

## Delivery rules

- Work in vertical, independently revertible slices.
- Establish a failing fixture/test or a recorded manual reproduction first.
- Separate moves, language translation, behavioral change, generated designer
  churn, and cleanup into reviewable commits.
- Keep one production owner for each behavior throughout migration.
- Do not claim a platform, compatibility path, format, or integration before the
  exact evidence is recorded.
- Promote data and protocol contracts before replacing their implementations.
- A milestone may be split; its gate may not be waived by renaming the release.
- Do not begin the next milestone identity or scope until the current `C -> E ->
  P` transaction has completed and verified exact `P` is on `master`.
- An owner-approved tracked amendment after a proposed freeze invalidates that
  candidate. Preserve its local evidence as superseded, create a new source
  commit, and repeat every candidate-specific gate; evidence never transfers by
  wording alone.
- When an exit gate cannot be satisfied, stop at the last qualified checkpoint;
  continue only machine-verifiable work that does not cross that boundary.

## Programme dependency map

```text

        |
1.x inventory + behavior oracles + settings/update tests
        |
Typed identity/domain + command contracts + C# substrate
        |
Native-profile specification + migrations + validator/migrator
        |
Workspace interaction proof
        |
Whole-document canonical convergence
        |

        |

        |
Application-backed CLI + optional qualified TUI
        |
Compatibility, accessibility, security, performance, OS convergence
        |
Reproducible portable payload -> optional Universal Setup promotion
```

AIDE may assist and record evidence alongside these stages; it never becomes a
runtime or release-truth dependency.

## Shared checkpoint transaction gates

Every milestone follows the canonical [release process](../development/releasing.md).
Freeze payload commit `C`; create `E` as its direct, single-parent child with
exactly the release catalogue and matching validation-record diff; record qualification `pass` and
promotion `unpromoted`; rebuild exact `E` byte-identically; and validate its full
SHA through create-only SHA-bound candidate transport while `dev/2.x` remains at
`C`. With exact-old leases, atomically fast-forward both permanent refs to `E`,
create the absent annotated tag, and consume the transport. Never promote moving
branch names.

The **alpha checkpoint gate** then creates direct, single-parent child `P` with
exactly the same two evidence files. `P` records `tagged / intentionally-unpublished /
unpublished / not-applicable / feed false`. Validate full `P` through its
create-only SHA-bound `attest/<tag>-post-<P>` ref while both permanent refs remain
at `E`, atomically fast-forward both `master` and `dev/2.x` to it with exact-old
leases, consume the temporary ref, and only
then begin the next identity. No GitHub release or alpha-feed promotion occurs.

The **public-prerelease checkpoint gate** publishes and re-verifies the exact
tagged packages. Successful `P` changes exactly the evidence pair plus
`release/feeds/beta/release.json` and records
`tagged / published / passed / feed true`. A public post-verification failure
changes exactly the evidence pair, records `published / failed / feed false`,
does not change the feed, and may be superseded by an immediate successor.
Either outcome is preserved; validate and promote exact `P` before starting a
successor identity. Betas and release candidates both use the beta channel and
public-prerelease policy.

The **stable checkpoint gate** is identical in transaction shape, with a
successful `P` owning `release/feeds/stable/release.json`. Under
[ADR 0010](../architecture/decisions/0010-stable-release-identity.md), stable
starts as a direct metadata-only commit from accepted RC source, then builds and
fully requalifies the newly stable bytes. RC/stable byte identity is never
claimed. No 2.x `VERSION` files are permitted in any gate.

## Alpha 1 — establish the safe 2.0 boundary

Outcome: the existing unpublished overhaul is honestly identified as 2.0
development without notifying legacy users or claiming a native-v2 format.

- [x] Preserve the modular-monolith and dual-build-lane foundation.
- [x] Add secure transactional legacy loading/saving and typed feature services.
- [x] Establish deterministic portable packaging and initial characterization.
- [x] Accept the 2.0 vision, scope, compatibility charter, and staged language
  strategy.
- [x] Preserve active 1.x maintenance on `dev/1.x`, its qualified ledger
  on `legacy/1.x`, the qualified 2.x ledger on `master`, and next-milestone 2.x
  integration on `dev/2.x`.
- [x] Preserve root and `legacy-1x/VERSION` solely for 1.x compatibility; use
  `release.json` for 2.x and give successful public `P` sole ownership of
  published beta/stable feed changes.
- [x] Set current build identity to `2.0.0-alpha.1` while retaining legacy
  catalogue writer `1.1.0`.
- [x] Apply canonical assembly/file/informational identity to every shipped
  managed binary and verify it mechanically.
- [x] Replace path/CPU-scoped `My.Settings` with one locked, atomic C3-owned
  profile; add bounded read-only 1.x import, recovery, future-schema protection,
  and automated retry/idempotency evidence. Keep real historical-profile,
  packaged cross-lane, corrupted-profile, and minimum-OS evidence in the release
  gate.
- [x] Make unpublished prerelease update discovery honor publication state and
  compare the complete release identity rather than numeric product version only.
- [x] Add the machine-readable release catalogue and promotion/tag validator.
- [x] Rebuild, package twice, and create new Alpha 1 validation evidence.
- [x] Encode a provider-neutral trusted-runner contract: prefer an isolated
  organization runner group and permit a repository-scoped ephemeral fallback
  with exact labels, manual dispatch, read-only credentials, trusted workflow
  control, and no untrusted pull-request execution.
- [ ] Configure the restricted GitHub qualification/development environments,
  branch and tag rules, and required owner approval before public Beta.
- [ ] Select a repository licence before the first public Beta tag/publication or
  before advertising external reuse. This is an owner decision, not an Alpha
  engineering gate or an automated refactor decision.

Exit gate: no legacy client is offered the alpha accidentally; metadata and
packages agree; both lanes and existing scenarios pass; old candidate evidence
remains immutable; critical catalogue and preference smoke paths have no known
data-loss defect; settings migration has automated logic evidence and every
deferred real-profile or minimum-OS check remains explicit.

Promotion gate: pass the shared alpha checkpoint gate for
`v2.0.0-alpha.1`. Because the workflow definition is not yet on the default
branch, run the exact-`E` candidate gate directly on the maintained compatibility
machine and record it. The tag push bootstraps workflow dispatch onto `master`.
Alpha 2 identity is not started before exact Alpha 1 `P` is verified on `master`.

`v2.0.0-alpha.2`; do not start Alpha 3 identity before exact Alpha 2 `P` is on
`master`.

## Alpha 6 — converge the complete canonical catalogue

Outcome: every supported entity and relationship has one format-neutral,
native-superset logical representation before canonical mutation becomes a
production authority.

- [x] Accept ADR 0012 and the canonical catalogue/Application contract.
- [x] Decide legacy identity durability, native-profile succession,
  temporal/uncertainty/provenance semantics, units/vocabularies, and stored-text
  versus comparison/search policy through focused ADRs and executable fixtures.
- [x] Define logical, current-profile, and export-profile validation separately;
  publish capability and representability projections for legacy and native
  profiles.
- [x] Define `CatalogueDocument`, transaction, snapshot, change-set, projection,
  versioned query, bounded cursor, and incremental/verifiable fingerprint
  contracts with explicit memory and complexity budgets.
- [ ] Project every supported legacy entity, relationship, counter, alias,
  timestamp, and measurement into the canonical document in read-only shadow
  mode.
  - Implemented: complete native-v2 DTO shadow fingerprint projection and
    native write/read semantic-root parity, including graphs migrated from v1.1.
  - Remaining: direct legacy-profile projection into the canonical logical
    entity graph with field/value evidence rather than a native DTO intermediary.
- [ ] Adapt both legacy and native readers/writers to the complete logical
  document and prove round-trip semantic equality, permitted normalization, and
  historical-reader compatibility.
- [ ] Run whole-document differential comparisons without replacing the active
  production mutation path.
- [ ] Enforce that `DataSet` and `Native*` objects stay below their profile
  adapter/characterization boundaries.

Exit gate: the complete supported catalogue round-trips through both applicable
profiles; snapshot/query/fingerprint resource models pass; no stable-profile
semantic blocker remains; and no active production document is divided between
canonical and legacy state. Alpha 6 introduces no new production frontend and no
canonical production mutation.

Promotion gate: pass the shared alpha checkpoint gate for
`2.0.0a6`; do not start Alpha 7 identity before exact Alpha 6 `P` is on

## Alpha 7 — introduce the Application document kernel

Outcome: one document/session lifecycle becomes the production authority and the
first canonical mutations prove it in both profiles.

- [ ] Add a C# 7.3/net40 `C3.Application` boundary with no WinForms, Console,
  XML, file, or OS mechanism dependency.
- [ ] Separate `DocumentSessionId`, optional durable `CatalogueId`, monotonic
  `ContentVersion`, semantic `StateFingerprint`, exact `DiskRevision`, and
  destination `LocationLease`.
- [ ] Implement and model-test document lifecycle, one-writer/snapshot-reader
  coordination, allowed actions, immutable events, operation descriptors,
  typed result/refusal/conflict taxonomy, progress, and cancellation.
- [ ] Move clocks and entity/operation/correlation ID generation out of
  frontends.
- [ ] Implement snapshot-based save, current/saved fingerprints, Save As leases,
  external-conflict actions, history/savepoints, bounded undo, and workspace
  recovery distinct from backup and migration journals.
- [ ] Promote the canonical document as the sole active state and confine the
  legacy `DataSet` to the v1.1 adapter.
- [ ] Migrate Brands and Cassette Models to Application/Catalogue requests,
  atomic change sets, resource-keyed results, profile-aware save/reopen, and
  shared conformance scenarios.
- [ ] Prove stale drafts, concurrent save of version N versus current N+1,
  failed save, external modification, destination replacement races, compound
  mutation, and cross-profile refusal behavior.

Exit gate: one active document authority serves Brands and Models in both
profiles; presentation owns no catalogue history or feature service; save
failure changes no active state; undo to the saved state becomes clean without
decreasing the content version; and recovery/conflict paths preserve user data.

## Release candidate — prove, do not redesign

- [ ] Freeze candidate source and dependencies.
- [ ] Pass automated, manual, accessibility, security, recovery, performance,
  update-channel, and minimum-OS gates on the exact artifacts.
- [ ] Package twice with identical hashes and inspect all binary identities.
- [ ] Test side-by-side 1.x/2.x operation, settings migration, catalogue rollback,
  and file associations.
- [ ] Publish as prerelease, download every artifact, and verify hashes and launch.
- [ ] Resolve all release-blocking defects without scope expansion.
- [x] Accept the RC/stable identity strategy in
  [ADR 0010](../architecture/decisions/0010-stable-release-identity.md): create a
  direct metadata-only stable commit from accepted RC source, rebuild and fully
  requalify the new stable bytes; any functional change requires another RC.

Promotion gate: the stable identity strategy must already be accepted. Then pass
the shared public-prerelease checkpoint gate using channel `beta` and publication
policy `public-prerelease`. Exact RC `P` must be on `master` before stable
promotion begins.

## Stable promotion

- [ ] Create the audited metadata-only stable transition from accepted RC source,
  rebuild and fully requalify the new stable bytes with no functional or payload-
  composition change, and apply the shared stable checkpoint gate so only a
  successful exact `P` changes matching stable `release.json` metadata.
- [ ] Record final tag, commit, workflow runs, VM evidence, asset URLs, sizes,
  hashes, signatures if used, and post-download checks.
- [ ] Publish known limitations and supported compatibility matrix.
- [ ] Preserve rollback assets and begin the documented 2.x maintenance policy.

## Post-2.0 horizons

Potential 2.1+ work includes richer reference packs and custom fields, media/J-card
handling, automatic three-way catalogue merge, rich CLI mutation, a deferred or
enhanced TUI, out-of-process extensions, additional export/report profiles, and
Universal Setup/AIDE capability expansion. ARM64, production AppKit/GTK/Qt
shells, multi-document windows, sync, accounts, and recognition assistance
require separate product and compatibility decisions; they are not inherited
promises.

## Definition of task completion

A checkbox is complete only when implementation, tests/fixtures, documentation,
both applicable build lanes, and the required manual evidence agree. A code merge
alone is not completion. If a requirement is removed, replace its checkbox with
an ADR link and explicit scope change rather than marking unimplemented work done.
