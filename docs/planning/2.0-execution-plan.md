# C3 2.0 execution plan

Status: **Active**  
Programme baseline: 4 August 2026

This is the one repository-owned implementation checklist for C3 2.0. It owns
dependency order, gates, and completion state. `ROADMAP.md` summarizes public
outcomes; GitHub Issues and future AIDE work units own individual assignments.
They link here instead of copying this checklist.

## Delivery rules

- Work in vertical, independently revertible slices.
- Establish a failing fixture/test or a recorded manual reproduction first.
- Separate moves, language translation, behavioral change, generated designer
  churn, and cleanup into reviewable commits.
- Keep one production owner for each behavior throughout migration.
- Do not claim a platform, compatibility path, format, or integration before the
  exact evidence is recorded.
- Promote data and protocol contracts before replacing their implementations.
- A milestone may be split; its gate may not be waived by renaming the release.

## Programme dependency map

```text
Governance and release isolation
        |
1.x inventory + behavior oracles + settings/update tests
        |
Typed identity/domain + command contracts + C# substrate
        |
Native-v2 specification + migrations + validator/migrator
        |
Workspace state + undo/recovery + OEM+ shell replacement
        |
Compatibility, accessibility, security, performance, OS evidence
        |
Reproducible portable payload -> optional Universal Setup promotion
```

AIDE may assist and record evidence alongside these stages; it never becomes a
runtime or release-truth dependency.

## Alpha 1 — establish the safe 2.0 boundary

Outcome: the existing unpublished overhaul is honestly identified as 2.0
development without notifying legacy users or claiming a native-v2 format.

- [x] Preserve the modular-monolith and dual-build-lane foundation.
- [x] Add secure transactional legacy loading/saving and typed feature services.
- [x] Establish deterministic portable packaging and initial characterization.
- [x] Accept the 2.0 vision, scope, compatibility charter, and staged language
  strategy.
- [x] Create permanent `master` (1.2 maintenance) and `dev` (2.0 integration)
  branches and document forward-port ownership.
- [ ] Separate root/legacy, alpha, beta, and stable update-feed ownership.
- [ ] Set current build identity to `2.0.0-alpha.1` while retaining legacy
  catalogue writer `1.1.0`.
- [ ] Apply canonical assembly/file/informational identity to every shipped
  managed binary and verify it mechanically.
- [ ] Add one-time idempotent migration of 1.x user preferences.
- [ ] Rebuild, package twice, and create new Alpha 1 validation evidence.
- [ ] Select a repository license before advertising external reuse. This is an
  owner decision, not an automated refactor decision.

Exit gate: no legacy client is offered the alpha accidentally; metadata and
packages agree; both lanes and existing scenarios pass; old candidate evidence
remains immutable; settings migration has automated logic evidence and a manual
profile test remains visible if not yet run.

## Alpha 2 — construct the 1.x compatibility laboratory

Outcome: “C3 1.x compatibility” becomes a bounded, executable matrix.

- [ ] Inventory public tags, binaries, settings schemas, update behavior, and all
  observed catalogue format variants (`1.0`, `1.0.1`, `1.0.2`, `1.1.0`, and any
  release-specific deviations).
- [ ] Preserve legal redistributable baseline readers or document a reproducible
  clean-room harness for each supported profile.
- [ ] Add privacy-safe golden fixtures, provenance manifests, expected normalized
  models, and corruption/security/culture variants.
- [ ] Classify characterized behavior as required, tolerated quirk, or defect.
- [ ] Test new-reader/old-writer and current-v1.1-writer/baseline-reader paths in
  both lanes.
- [ ] Test settings migration with old, missing, malformed, and repeated profiles.
- [ ] Add update-channel contract tests and promotion dry runs.
- [ ] Define the exact 1.x maintenance/support baseline; do not imply every alpha
  ever emitted is a stable support target.

Exit gate: the compatibility matrix names all supported producers and every row
has automated or explicitly pending manual evidence; no broad “fully compatible”
claim remains unqualified.

## Alpha 3 — stabilize identity, commands, and the C# substrate

Outcome: one typed domain can support legacy and native persistence and a new UI
without leaking `DataSet` or mutable display-name identity.

- [ ] Accept entity vocabulary and aggregate boundaries, including the distinction
  between a deck model and a physical `DeckUnit` if both are required.
- [ ] Define stable-ID, equality, ordering, timestamp, optional-value, validation,
  and relationship invariants.
- [ ] Define command, draft, result, change-set, and undo contracts.
- [ ] Add deterministic synthetic catalogue generators and domain property tests.
- [ ] Freeze the current VB catalogue-library public behavior and API surface.
- [ ] Port one small vertical catalogue slice mechanically to explicit C# 7.3;
  differential-test it against the VB oracle.
- [ ] Port remaining catalogue and infrastructure slices only after each prior
  slice passes; never combine a port with redesign.
- [ ] Remove the superseded production implementation after promotion so there
  is still one behavior owner.

Exit gate: the domain has no WinForms/XML/`DataSet` dependency, stable identity is
proven, commands drive mutations, and promoted C# slices pass the legacy matrix.

## Alpha 4 — implement native-v2 persistence and migration

Outcome: C3 has two explicit persistence profiles joined by deterministic,
auditable transitions.

- [ ] Accept ADR 0005 and freeze catalogue format 2.0.0 invariants.
- [ ] Publish schema, canonical examples, security limits, normalization vectors,
  and a machine-readable support matrix.
- [ ] Implement independent native-v2 reader and deterministic writer.
- [ ] Implement dry-run conversion, deterministic mapping, transactional
  convert-copy, and migration reports.
- [ ] Implement legacy mode and loss-aware v1.1 export with baseline-reader proof.
- [ ] Implement a minimal validator/migrator CLI using the same application/domain
  contracts rather than duplicating format logic.
- [ ] Add recovery-journal and interrupted-operation tests.

Exit gate: both lanes and the CLI agree on canonical models and files; repeat
migrations are stable; no operation silently overwrites a legacy original; export
loss reporting is complete.

## Alpha 5 — build workspace foundations

Outcome: application state and reusable interaction patterns are ready for a new
shell without duplicating domain behavior.

- [ ] Replace the last global document seam with explicit composition and a
  document/workspace controller.
- [ ] Make session, selection, filter, draft, dirty, compatibility, recovery, and
  background-operation ownership explicit.
- [ ] Implement command history and practical undo/redo.
- [ ] Build reusable field definitions, validation presentation, list, inspector,
  empty-state, error, and progress patterns.
- [ ] Prototype the OEM+ shell in C# 7.3 against the same application contracts.
- [ ] Prove one complete feature end to end in both lanes before expanding.

Exit gate: one production workflow uses the new shell patterns with behavior,
designer, keyboard, accessibility, DPI, and performance parity; no storage rule
was copied into presentation code.

## Alpha 6 — complete the OEM+ workflow replacement

Outcome: all accepted 2.0 workflows use one coherent workspace.

- [ ] Migrate brand, model, deck, tape, search, statistics, settings, diagnostics,
  migration, import/export, and recovery surfaces feature by feature.
- [ ] Add bulk previews, undo coverage, stable selection, persistent views, and
  helpful empty/error states where in scope.
- [ ] Complete accessibility names/roles, keyboard navigation, high contrast,
  localization readiness, and DPI matrices.
- [ ] Remove obsolete forms after their replacement gates pass.
- [ ] Decide from evidence whether any remaining VB presentation source can ship
  temporarily; record an owner and exit gate for every retained slice.

Exit gate: the 2.0 feature surface is behaviorally complete and one implementation
owns each workflow; no release-blocking parity, accessibility, or data-safety gap
remains.

## Beta 1 — feature complete and compatibility complete

- [ ] Freeze stable scope, public command/model contracts, file profiles, and user
  terminology.
- [ ] Pass the complete 1.x matrix, migration/export matrix, and two-lane
  differential suite.
- [ ] Complete user guide, migration/rollback guide, recovery guide, and release
  notes from verified behavior.
- [ ] Capture baseline performance budgets and resolve release-blocking regressions.
- [ ] Run security review of XML, extension envelopes, paths, reports, logs, and
  update metadata.

No new feature enters after Beta 1 without removing equivalent risk/scope and
recording the decision.

## Beta 2 — distribution and operational hardening

- [ ] Reproduce portable payloads and validate clean-machine behavior.
- [ ] If Universal Setup's binding contract is stable, generate a C3 binding and
  prove install/verify/repair/rollback/uninstall against identical payload hashes.
- [ ] Keep portable distribution complete if setup promotion is deferred.
- [ ] Exercise AIDE only at capabilities its pinned version actually provides;
  compare AIDE evidence with native C3 gate output.
- [ ] Complete privacy review and user-consent flow for support bundles.

## Release candidate — prove, do not redesign

- [ ] Freeze candidate source and dependencies.
- [ ] Pass automated, manual, accessibility, security, recovery, performance,
  update-channel, and minimum-OS gates on the exact artifacts.
- [ ] Package twice with identical hashes and inspect all binary identities.
- [ ] Test side-by-side 1.x/2.x operation, settings migration, catalogue rollback,
  and file associations.
- [ ] Publish as prerelease, download every artifact, and verify hashes and launch.
- [ ] Resolve all release-blocking defects without scope expansion.

## Stable promotion

- [ ] Promote unchanged RC artifacts and matching stable feed metadata.
- [ ] Record final tag, commit, workflow runs, VM evidence, asset URLs, sizes,
  hashes, signatures if used, and post-download checks.
- [ ] Publish known limitations and supported compatibility matrix.
- [ ] Preserve rollback assets and begin the documented 2.x maintenance policy.

## Post-2.0 horizons

Potential 2.1+ work includes richer reference packs and custom fields, media/J-card
handling, catalogue merge, rich CLI automation, out-of-process extensions,
additional export/report profiles, and Universal Setup/AIDE capability expansion.
ARM64, alternate shells, sync, and recognition assistance require separate
product and compatibility decisions; they are not inherited promises.

## Definition of task completion

A checkbox is complete only when implementation, tests/fixtures, documentation,
both applicable build lanes, and the required manual evidence agree. A code merge
alone is not completion. If a requirement is removed, replace its checkbox with
an ADR link and explicit scope change rather than marking unimplemented work done.
