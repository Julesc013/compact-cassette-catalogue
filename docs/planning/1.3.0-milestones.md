# C3 1.3.0 milestone ladder

The final original C3 release uses four explicit checkpoints. A later stage
inherits every earlier gate; it does not reinterpret missing evidence as passed.
The [post-Alpha owner decision](../governance/1.3.0-three-lane-matrix-2026-08-05.md)
replaces Alpha's four diagnostic lanes with exactly three Beta/stable release
lanes while preserving the immutable Alpha record.

The [preview release authorization](../governance/1.3.0-release-authorization-2026-08-05.md)
permits Codex to create deliberate Alpha tags and retained Alpha distributions
after their checks. Every Beta tag, Beta-labelled distribution, or Beta
publication requires separate explicit human approval even after its technical
gates pass.

| Milestone | Tag | Purpose | Publication |
| --- | --- | --- | --- |
| Alpha 1 | `v1.3.0a1` | Freeze the corrected three-anchor ancestry, maintenance doctrine, compatibility evidence, and validation/build scaffolding | Annotated source tag only; intentionally unpublished |
| Alpha 2 | `v1.3.0a2` | Prove the authoritative three-lane build, immutable-lock, deterministic-package, and builder-smoke control path | Retained engineering ZIPs; intentionally unpublished |
| Beta 1 | `v1.3.0b1` | Complete all approved runtime repairs, settings continuity, framework lanes, packaging, and compatibility qualification | Requires explicit human approval even to tag or retain Beta-labelled ZIPs; public prerelease needs separate approval |
| Stable | `v1.3.0` | Rebuild and fully qualify the accepted Beta source under stable identity, publish retained bytes, verify downloads, and promote the legacy feed | Public stable release |

There is no C3 1.2.1 release. There is no planned feature milestone after 1.3.0.

## Alpha 1 exit

Alpha 1 proves that future work starts from the right program and is guarded
against architectural drift. It does not claim that known baseline defects are
fixed or that any operating-system support matrix has been rerun.

Required:

- direct development ancestry from `58a5b7d...`;
- exact runtime genome from `509c9ec...` and release evidence at `v1.2.0b1`;
- immutable reachability of the superseded refactor tip;
- complete maintenance governance, roadmap, TODO, changelog, notes, and plans;
- projected historical catalogue/settings evidence and strict validation;
- passing baseline-genome gate with no undocumented exception;
- source-identical four-lane build configuration;
- diagnostic compilation and binary metadata verification on available tools;
- exact verification of official `v1.2.0b1` assets; and
- an evidence record that lists every deferred authoritative/manual gate.

The four-lane item above is an Alpha historical result, not a continuing
publication requirement.

## Alpha 2 exit

Alpha 2 proves that the ratified three-lane release machinery can produce an
honestly labelled, retained engineering checkpoint before runtime repair. It
requires serviced builders, one clean pushed source, one external immutable
lock, Preparation and Candidate builds, final source closure, exact `1.3.0a2`
package identity, path-distinct deterministic reproduction, x86/x64 builder
smoke, and an annotated evidence-complete tag. Historical Gate 1, application
repairs, native ARM64 runtime execution, and minimum-OS qualification remain
explicitly deferred.

## Beta 1 entrance and exit

Beta implementation begins only when the remaining baseline reconstruction work
is completed or an owner-approved change to that gate is recorded. Beta 1 is
feature complete and compatibility complete for the final 1.3 scope.

It exits only with:

- every S0–S2 item in the salvage ledger resolved or explicitly rejected after
  reproduction proves it does not exist;
- Gate 2 lifecycle/data-safety work complete;
- Gate 3 referential/counter work complete;
- Gate 4 settings migration complete;
- Gate 5 lanes and portable packages complete;
- native ARM64 AA64 output and Windows-on-ARM target execution proved;
- automated historical and reverse-compatibility matrices passing;
- required manual workflows passing on retained package bytes;
- no new runtime DLL, catalogue format, source topology, or UI divergence; and
- a complete Beta validation record with exact source, package, and toolchain
  identities; and
- explicit human approval before the Beta tag or any Beta-labelled distribution
  is created.

## Stable entrance and exit

Stable starts from an owner-accepted Beta 1 source. The stable source transition
may change version/stage/date and release-facing projections only. A functional
change requires a new beta checkpoint rather than a silent stable repair.

Stable exits only after two clean path-distinct builds, deterministic package
comparison, the full OS/manual matrix, immutable tagging, publication of the
already-qualified bytes, clean re-download verification, and final feed/branch
promotion.

## Cross-milestone risks

| Risk | Control | Release impact |
| --- | --- | --- |
| Refactor architecture leaks into 1.x | genome manifest, one-project rule, diff review | Blocks commit |
| A failed load/save damages active data | temporary state, transactional save, fault tests | Blocks Beta/stable |
| Old settings silently reset | real isolated profiles plus fixture validation | Blocks Beta/stable |
| Newer frameworks change behaviour | identical source/resources and cross-lane exchange | Blocks affected lane |
| ARM64 silently falls back to x64/AnyCPU | closed PE/CorFlags inspection plus native target-process proof | Blocks Beta/stable |
| Preview metadata advertises unavailable bytes | feed isolation validator | Blocks tag/publication |
| Qualification rebuild changes bytes | retain artifacts; publish without rebuilding | Blocks publication |
| Classic Windows claim lacks evidence | stage-specific OS matrix and explicit deferral | Claim removed or release blocked |
| Candidate lock is self-referential, stale, or detached from source | immutable external lock, clean remote-bound source, retained lock SHA-256 | Blocks candidate build |
| Three individually valid packages use different release/source/lock identities | one closed package-evidence set with one stage label, source, and lock | Blocks package creation |
| Provider ref was stale at freeze | explicit fetch receipt captured before offline builds | Blocks lock capture |
| Candidate builds mutate or drift from frozen source | final source/ref/genome/lock closure after all lanes | Blocks Candidate packaging |
| Extracted directory does not come from verified ZIP | authenticated five-entry manifest with length/SHA-256 closure | Blocks target launch |

The detailed work and evidence live in the milestone-specific plans and the
qualification matrix.
