# C3 2.0 grand programme

Status: **Authoritative programme map**

Programme: **C3 2.0.0**

Active integration branch: **`dev/2.x`**

Current release-train milestone: **Alpha 5**

This document is the concise map for the complete C3 2.0 overhaul. It defines
the result, dependency order, workstreams, and delivery discipline. It does not
copy detailed contracts from their owners: the linked architecture, product,
compatibility, UI, persistence, testing, and release documents remain
authoritative for their subjects.

## Ultimate product outcome

C3 2.0 is one dependable, local-first cassette catalogue product with:

- one native-superset logical catalogue and one production mutation authority;
- loss-aware compatibility with supported C3 1.x catalogues;
- deterministic native storage and explicit constrained legacy profiles;
- a complete, resizable, keyboard-accessible OEM+ Windows interface;
- x86/.NET Framework 4.0 and x64/.NET Framework 4.8 delivery lanes;
- a bounded automation-grade CLI over the same application behavior;
- portable archives as the canonical payload and optional setup as a consumer;
- transactional saves, conflict detection, recovery, undo, and diagnostics;
- internal modular boundaries that permit future shells without compromising
  the Windows 2.0 release; and
- repository-owned, reproducible evidence for every promoted checkpoint.

The product is future-ready by preserving stable data/process contracts and
clear ownership, not by implementing every possible platform, plugin, or cloud
feature before 2.0 can ship.

## Non-negotiable architecture

```text
Windows / CLI / optional TUI
             |
             v
       C3.Application
             |
             v
       C3.Catalogue
             |
             v
         C3.Domain

Composition roots assemble inward-facing ports implemented by C3.Infrastructure.
```

`C3.Domain` owns foundational value semantics. `C3.Catalogue` owns the complete
logical graph and atomic catalogue behavior. `C3.Application` owns use-case and
document lifecycle coordination. `C3.Infrastructure` owns external mechanisms.
Frontends own only medium-specific parsing, interaction, and rendering.

These rules apply throughout the transition:

1. There is exactly one production mutation authority.
2. A supported document is never split between independently mutable canonical
   and legacy representations.
3. Persistence DTOs, `DataSet`, XML, paths, clocks, and UI toolkits never become
   catalogue-domain dependencies.
4. Frontends never manufacture authoritative identifiers, audit times,
   save-state decisions, or English result messages.
5. A profile limitation is not a universal logical invariant.
6. Refused, stale, failed, cancelled, or invalid operations change nothing.
7. Every replacement save verifies expected document and destination state.
8. Stable external contracts are versioned data/process schemas and codes; the
   current CLR assemblies are not a promised third-party SDK.

## Canonical transition

The transition is whole-document and evidence-driven:

```text
complete legacy document
        |
        v
read-only canonical shadow
        |
        v
legacy/native adapter round trips
        |
        v
whole-document differential proof
        |
        v
canonical production ownership
        |
        v
feature mutation migration
```

Before promotion of canonical ownership, every supported Brand, cassette model,
deck model, deck unit, tape, side, recording, relationship, counter, alias,
timestamp, measurement, and compatibility behavior must have a deterministic
projection and an explicit equivalence rule. There is no feature-by-feature
dual-write bridge.

The logical model is a native superset. It independently reports logical
validity, direct-save validity for the current profile, and representability
and loss for a requested export profile.

Legacy v1.1 identity remains session-scoped. No sidecar or private legacy XML
extension is introduced. Native conversion establishes durable identity. The
accepted Alpha 4 native profile is immutable; a changed semantic contract gets
a new profile identifier and explicit migration.

## Document kernel

The permanent model separates:

```text
DocumentSessionId   one open process session
CatalogueId         optional durable native catalogue identity
ContentVersion      monotonic in-session mutation version
StateFingerprint    versioned logical-content equality
DiskRevision        externally observed persisted-byte identity
LocationLease       authority for create or observed-revision replacement
```

Transactions are expected-version, validated, and atomic. Snapshots are
immutable and version-bound without requiring a full deep copy after every
edit. Queries use typed bounded expressions, stable ordering, entity-ID
tie-breakers, and version-bound cursors. Derived indexes are discardable and
rebuildable. Bulk and destructive actions use version-bound operation plans.

`C3.Application` is introduced only after complete canonical convergence. It
will own lifecycle, operation dispatch, allowed actions, history/savepoints,
recovery policy, progress/cancellation, clocks and IDs, events, and external
ports. It will not own catalogue rules, XML, files, WinForms, console rendering,
or terminal state.

## Product workstreams

The overhaul is delivered through dependent workstreams rather than a big-bang
rewrite:

1. **Compatibility laboratory** — historical formats, readers, behaviors,
   fixtures, and claims remain executable.
2. **Semantic catalogue** — complete native-superset graph, value semantics,
   identities, validation, transactions, snapshots, fingerprints, and queries.
3. **Persistence profiles** — strict readers/writers, capability projections,
   transactionality, migration, export, backups, conflict copies, and recovery.
4. **Application kernel** — lifecycle, operations, results, plans, history,
   save coordination, events, availability, progress, and cancellation.
5. **Windows presentation** — shared C# WinForms implementation, responsive
   task-oriented shell, reusable patterns, accessibility, DPI, and both lanes.
6. **Workflow migration** — Brands, models, decks, tapes, recordings, search,
   statistics, settings, diagnostics, migration/export, import, and recovery.
7. **Automation** — CLI commands and schema-versioned machine results over the
   same Application operations.
8. **Optional terminal experience** — TUI only if independently usable and
   qualified; otherwise explicitly deferred.
9. **Operations and trust** — deterministic builds, package manifest, update
   channels, signing policy, SBOM/provenance policy, setup binding, and release
   evidence.
10. **Sustainability** — concise ownership documentation, architecture fitness
    tests, contribution guidance, performance budgets, and forward-compatible
    data/process contracts.

## Implementation order from the current repository

The dependency-correct Alpha 6 work order is:

1. introduce document identity, content-version, fingerprint, and identity-
   durability primitives with executable contracts;
2. decide remaining semantic policies through focused ADRs and fixtures;
3. define format-neutral logical entity and metadata types without reusing
   `Native*` persistence DTOs;
4. define complete read-only `CatalogueDocument` snapshots and graph indexes;
5. build the legacy-to-canonical whole-document shadow adapter;
6. build current-native-profile to/from canonical adapters;
7. define explicit logical/profile/export validation and capability results;
8. prove deterministic fingerprints and whole-document semantic equivalence;
9. add bounded query/cursor contracts and resource budgets; and
10. enforce adapter-only `DataSet` and `Native*` ownership in the build.

Foundation contracts and tests may land on the moving integration branch before
Alpha 5 promotion only when they do not alter the production mutation owner or
claim Alpha 6 qualification. Such a change supersedes the current Alpha 5
candidate and requires the complete Alpha 5 freeze and owner matrix to be rerun.

## Slice protocol

Every implementation slice follows the same discipline:

1. name one behavior owner and the boundary being replaced or introduced;
2. add a failing deterministic test, fixture, or characterization first where
   practical;
3. keep moves, translations, behavior changes, and cleanup distinguishable;
4. update the relevant ADR/contract and compatibility effect;
5. run focused tests after each behavioral change;
6. run `build/verify.ps1 -Rebuild` before integration;
7. make a small, descriptive, independently revertible commit;
8. push only the moving integration branch;
9. remove a superseded owner only after replacement proof; and
10. never convert absent manual or minimum-OS evidence into a pass.

## Quality and evidence

The programme adds or preserves:

- model-based lifecycle testing;
- property-based mutation sequences;
- metamorphic migration/export tests;
- adapter conformance scenarios shared by legacy and native profiles;
- deterministic state-fingerprint vectors;
- crash-point testing around save, replace, journal, and recovery boundaries;
- query/cursor stale-version and resource-exhaustion tests;
- differential behavior across x86/net40 and x64/net48;
- exact-package workflow and cross-lane reopen tests;
- real DPI, keyboard, high-contrast, screen-reader, and minimum-OS matrices; and
- two clean path-distinct package builds with byte equality.

Automated layout or accessibility metadata tests do not replace real display or
assistive-technology evidence. Performance claims always name the fixture,
host, measurement method, and budget.

## Release and publication discipline

```text
dev/2.x     moving 2.x integration
master      qualified current-generation ledger
dev/1.x     moving bounded 1.x maintenance
legacy/1.x  qualified 1.x ledger
```

Branches and tags do not imply publication. Qualified Alpha tags remain
unpublished. Beta requires owner acceptance of exact frozen packages before
promotion, tag, GitHub prerelease, downloaded-asset verification, and beta-feed
promotion. Stable is an unchanged qualified RC promotion.

The readable release label remains `2.0.0-alpha.N` across binaries, packages,
feeds, and evidence. New Git tags use the compact mapping `2.0.0aN`,
`2.0.0bN`, `2.0.0rcN`, and `2.0.0`; immutable Alpha 1–4 tags retain their
historical names. One resolver owns this mapping, and the catalogue records the
actual tag so history is never re-derived or rewritten.

## Explicitly deferred from compulsory 2.0 scope

- ARM64 and non-Windows production shells;
- cloud accounts, hosted sync, or mandatory online services;
- automatic semantic merge;
- multiple simultaneously open catalogue windows;
- in-process binary plugins or a general scripting language;
- C/C++ catalogue implementations;
- a broad mutation/query language exposed over the CLI;
- a mandatory installer or automatic self-updater; and
- AI recognition or hosted metadata enrichment.

These capabilities may be enabled later by stable catalogue/Application
contracts. None is permitted to delay a safe, complete Windows 2.0 release
without an explicit scope amendment.

## Definition of success

C3 2.0 succeeds when the product has no known release-blocking data-safety,
compatibility, security, accessibility, or workflow defect; every accepted
workflow has one owner and reproducible evidence; supported 1.x data can be
opened, converted, and exported under truthful loss rules; both Windows lanes
behave equivalently; exact release artifacts are reproducible and verified; and
future contributors can determine ownership and extension points from the
repository without reverse-engineering hidden conventions.
