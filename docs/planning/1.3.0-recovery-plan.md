# C3 1.3.0 recovery and qualification plan

Status: corrected 58a-derived baseline, Alpha 1, and the retained Alpha 2
three-lane control checkpoint are qualified and tagged. Alpha 3 is active;
historical Gate 1 remains open and still precedes application behaviour changes.

The [ratified post-Alpha owner decision](../governance/1.3.0-three-lane-matrix-2026-08-05.md)
supersedes the earlier four-lane release plan. The immutable Alpha result stays
historically accurate; Beta and stable use exactly three release lanes.

The [preview release authorization](../governance/1.3.0-release-authorization-2026-08-05.md)
allows deliberate Alpha tags and retained Alpha distributions after their
checks. Every Beta tag, Beta-labelled distribution, and Beta publication still
requires explicit human approval.

## Outcome

C3 1.3.0 is C3 1.2.0 Beta 1 completed, not the 2.0 architecture pushed back
into a legacy release. `58a5b7d...` is the direct development baseline,
`v1.2.0b1` / `2413e913...` is the qualified behavioural checkpoint, and
`509c9ec...` is the exact runtime source/genetic baseline. `v1.1.2` is the
earlier stable compatibility oracle. The archived 1.2.1/refactor work supplies
defect reports, regression cases, specifications, fixtures, build techniques,
and narrowly reusable patch intent only.

> Preserve the 1.2.0 Beta 1 program; repair it. Do not redesign it into another
> program.

No C3 1.3 runtime implementation begins before Gate 1 passes.

Milestone execution is split into [Alpha 1](1.3.0-alpha.1.md), the three-lane
[Alpha 2](1.3.0-alpha.2.md) control checkpoint, [Alpha 3](1.3.0-alpha.3.md)
legacy reliability/setup checkpoint, [Beta 1](1.3.0-beta.1.md), and
[stable](1.3.0-stable.md). The compact operational view is maintained in the
repository-root `TODO.md`.

A mechanical baseline-genome check must fail any unapproved difference.

| Root namespace | `Compact_Cassette_Catalogue` |
| Assembly name | `Compact Cassette Catalogue` |
| Project GUID | `{DD0ADBE8-82D1-4620-8073-FF8EC6392135}` |
| Startup object | `Compact_Cassette_Catalogue.My.MyApplication` |
| Settings section | `Compact_Cassette_Catalogue.My.MySettings` |

| Dependencies | No third-party runtime dependency |

| Updates | Optional, offline-first, nonfatal legacy three-line feed |
| Distribution | Portable packages are authoritative; qualified offline classic setup bundles are optional secondary distributions |

The genome manifest records and compares:

- production file paths;
- form and module type names;
- designer control names;
- `.resx` resource keys;
- application identity, project GUID, and framework assembly references;
- settings names, types, scopes, and defaults;
- DataSet table, column, type, order, and primary-key signatures;
- catalogue format constant and supported-format list;
- original update endpoint and default policy; and
- icon and principal UI asset hashes.

Additional release rules:

- no production source move or rename;
- no new production assembly;
- no C# production source on `dev/1.x`;
- no target-framework feature divergence;
- no bulk designer regeneration;
- no migration of catalogue identifiers for internal cleanliness;
- no XML format rewrite; and
- no whole-file replacement where a small patch is sufficient.

An allow-list entry is exceptional. It must name the changed surface, explain
the user-visible need, identify its regression proof, and receive review in the
same commit as the intentional difference.

## Source-identical three-lane release matrix

Use one original VB.NET project and one physical production source tree. Clean
builds override only `PlatformTarget`, `TargetFrameworkVersion`, `AppConfig`,
output directories, intermediate directories, and framework-specific
manifest/config metadata.

| Lane | Status | Primary release toolchain | Purpose |
| --- | --- | --- | --- |
| `win-x86-net40` | Required | Latest serviced VS2017 15.9 / MSBuild 15 locked at freeze | XP-era x86 compatibility floor |
| `win-x64-net48` | Required | Latest serviced VS2022 17.14 / MSBuild 17 locked at freeze | One general x64 package from Windows 7 SP1 onward |
| `win-arm64-net481` | Required | Latest stable serviced VS2026 / MSBuild 18 locked at freeze | Native Windows 11 ARM64 package |

The `v1.2.0b1` x64/net40 executable remains in the historical compatibility
corpus. It proves catalogue exchange, settings migration, side-by-side use,
rollback, and transition to 1.3 x64/net48. It is not rebuilt as a 1.3 package.
There is no x64/net481 release; the net481 lane exists specifically for native
ARM64.

All lanes compile identical forms and logic. `#If NET48` or equivalent
behavioural branching is prohibited. The original `ToolsVersion="14.0"`
declaration remains genetic metadata, while each lane overrides and verifies
its effective tools version, disables shared compilation, produces a binary
log, and records the actual compiler/reference assembly/resource-generator
paths and hashes.

Candidate authority is an immutable external lock, never a tracked file that
attempts to name its own commit. The lock binds clean source commit `C`, the
exact expected remote ref, Visual Studio/MSBuild/VBC/reference/ResGen inputs,
and its own retained SHA-256. Candidate mode rejects dirty source, stale
servicing floors, remote mismatch, changed locks, and non-rebuild invocation
before trusting output.

## Salvage boundary

Safe non-runtime evidence to copy or project onto the reconstructed lineage:

- catalogue 1.1.0 specification and schema;
- valid, invalid, culture, and XML-security fixtures;
- exact historical release provenance and SHA-256 corpus;
- historical reader/writer matrix;
- PE architecture and binary metadata checks;
- deterministic ZIP and payload verification techniques;
- documentation-link checks;
- compatibility and release validation templates;
- branch/release governance; and
- separation of hosted static checks from maintained Windows builders.

Runtime outcomes from the refactor are reimplemented narrowly in original
files. The detailed item, source, and test status is maintained in
[the salvage ledger](1.3.0-salvage-ledger.md).

The following remain strictly in 2.0:

- `C3.Catalogue`, `C3.Infrastructure`, and `C3.Domain` production assemblies;
- project splitting, modular-monolith structure, and production relocation to
  `src/`;
- aggregate, service, repository, or global-state replacement;
- C# translation;
- replacement of the existing DataSet model;
- broad elimination of default forms;
- the C3-owned XML preference profile or a native-v2 data format;
- extension/plugin or import/export frameworks;
- broad UI, DPI, layout, or localization reconstruction; and
- the 2.x updater manifest and release-train architecture.

## Gate 1 — exact baseline reconstruction

No production code changes are permitted until all required Gate 1 evidence is
present.

- [x] Retrieve and cryptographically verify the Microsoft Build Tools 2015
  Update 3 bootstrapper at exact version `14.0.25420.1`; this is lab input, not
  proof that the historical compiler is installed or that a rebuild passed.
- [ ] Build `v1.2.0b1` x86/net40 with recorded VS2015/MSBuild 14.
- [ ] Build `v1.2.0b1` x64/net40 with recorded VS2015/MSBuild 14.
- [x] Download official tagged artifacts and verify their recorded SHA-256.
- [ ] Repeat the recorded workflows in disposable environments.
- [x] Generate and commit the baseline genome manifest.
- [ ] Preserve representative real catalogues only as private test copies.
- [ ] Record screenshots and control/resource signatures.
- [ ] Prove `v1.1.2` and `v1.2.0b1` open the same canonical catalogue.

This gate reconstructs 1.2 history only. VS2015/MSBuild 14 is the historical
1.2 oracle; it is not authoritative for any 1.3 release lane.

## Gate 2 — data-loss and lifecycle repairs

Each item is a separate commit with a reproduction and regression test:

1. resolve pending tape edits before document transitions;
2. replace recursive close cancellation with an explicit close gate;
3. stop Save As cancellation from continuing;
4. remove the duplicate Open dialog after save-before-open;
5. load into temporary state before replacing the active catalogue;
6. save by verified same-directory temporary file, backup, and replacement;
7. detect external modifications with a simple revision/hash check;
8. replace positional tape update mapping with explicit named assignments; and
9. preserve existing identifiers and creation dates.

Classic-path temporary names must remain short and in the destination directory.

## Gate 3 — referential and counter integrity

Implement the following as direct DataTable-era repairs:

- model editor notes read from `Models`, not `Brands`;
- deck deletion updates the deck counter, not the tape counter;
- referenced brand/model/deck deletion is blocked;
- brand rename preserves relationships;
- runtime counts derive from actual rows;
- tape sequence allocation uses the maximum existing sequence;
- a bulk insertion validates completely before adding any row;
- each bulk copy receives its own sequence; and
- per-model tape counters reflect actual rows.

Do not normalize every file on load. Repair when the user performs the relevant
mutation, when save must correct a derived counter, or when the active catalogue
would otherwise become inconsistent.

## Gate 4 — settings continuity

Retain `My.Settings`. Add a user-scoped Boolean marker named
`settingsUpgradeRequired`, defaulting to `True`, only when the implementation
and tests are ready together.

First 1.3 startup must attempt `My.Settings.Upgrade()`, normalize only known
values, clear the marker after success, and save. Failure must not block startup,
must leave the marker armed, and must never modify or delete old `user.config`
files. Unknown update values normalize to `never`; existing message and
directory preferences survive; startup performs no new network request.

Required transitions:

- 1.1.2 to 1.3 x86/net40;
- 1.2.0b1 x86 to 1.3 x86/net40;
- 1.2.0b1 x64/net40 to 1.3 x64/net48;
- 1.3 x86/net40 to 1.3 x64/net48;
- 1.3 x64/net48 to 1.3 ARM64/net481;
- clean install without a previous profile;
- corrupt or inaccessible previous profile; and
- repeated startup after successful migration.

A read-only legacy profile locator is permitted only if the standard upgrade
cannot cover supported portable/package transitions.

## Gate 5 — three release lanes

Add net48 and native ARM64/net481 only after original net40 behaviour is stable.
Prove:

- an identical source manifest and resource set across lanes;
- no lane-specific application code;
- correct PE architecture and `TargetFrameworkAttribute`;
- x86 `0x014c`/PE32/32BITREQ, x64 `0x8664`/PE32+, and ARM64
  `0xaa64`/PE32+ with ILONLY CorFlags;
- exact settings schema parity;
- cross-lane catalogue exchange;
- no additional runtime DLL payload;
- an authenticated retained entry manifest binds the transferred ZIP to every
  extracted file name, length, and SHA-256;
- target-side scripts execute under Windows PowerShell 2 and derive exact OS
  build, service pack, native architecture, and Full Framework state;
- identical offline-first update defaults; and
- no framework-driven DPI or layout change.

Build proof and target-runtime proof are separate. Builder verification compiles,
inspects, and deterministically packages each lane. Target verification checks
the transferred package hash and executes workflows on XP SP3 x86, Windows 7
SP1 x64, or Windows 11 RTM ARM64. An x64 builder cannot runtime-qualify ARM64.

## Manual qualification contract

Run against the exact final package bytes:

- launch, close, New, Open, Save, Save As, and Save As cancellation;
- add/edit/delete brands, models, decks, and single/bulk tapes;
- tape editing, list views, filters, and scrolling with pending edits;
- close/open/new/scroll with pending edits;
- Save/Discard/Cancel at every document transition;
- invalid and unsupported XML;
- externally modified catalogue;
- read-only and unavailable destinations;
- backup recovery;
- console display and export;
- settings persistence and upgrades from isolated real profiles;
- automatic update checks disabled by default;
- manual update check with the network blocked;
- browser launch failure;
- side-by-side 1.2/1.3 use of catalogue copies; and
- rollback to 1.2 using a 1.3-written catalogue.

Minimum operating-system evidence:

| Package | Minimum qualification |
| --- | --- |
| x86/net40 | Windows XP SP3 x86 with .NET Framework 4.0 Full and a separately recorded final 4.0.3 state |
| x64/net48 | Fully serviced Windows 7 SP1 x64 with .NET Framework 4.8, plus later x64 Windows smoke tests |
| ARM64/net481 | Windows 11 21H2/RTM ARM64 with separately installed .NET Framework 4.8.1 and native-process proof |

## Release identity and payload

```text
Product version:        1.3.0
Stage:                  Release
Catalogue format:       1.1.0
Language/UI:            VB.NET / WinForms
Update default:         never
Distribution authority: portable ZIP
```

There is no 1.2.1 release. Accepted fixes appear in the 1.3.0 changelog without
presenting the refactor architecture as a product change.

Recommended artifacts:

```text
C3-v1.3.0-win-x86-net40-portable.zip
C3-v1.3.0-win-x64-net48-portable.zip
C3-v1.3.0-win-arm64-net481-portable.zip
SHA256SUMS.txt
```

Each portable ZIP contains the executable, matching config, README, release
notes, BUILD.txt, and a licence only after the owner selects one. No standalone
EXE is the authoritative download. A qualified optional setup ZIP may contain
the matching lane's `SETUP.exe`, adjacent immutable payload/manifest, and the
uninstaller installed by that setup. It must consume the exact qualified
portable payload bytes and add no application DLL graph. No MSI, MSIX,
ClickOnce publication, network bootstrapper, service, updater, or self-contained
runtime belongs in C3 1.3. Universal Setup may later consume the same contracts
as an independent programme; it does not block or redefine stable.

## Publication sequence

1. Put final `1.3.0 / Release` identity in the candidate before qualification.
2. Freeze exact source commit `C`, explicitly fetch and retain its provider-ref
   receipt, and capture the immutable external toolchain lock.
3. Build twice from clean, different absolute paths using that same lock and no
   further network dependency.
4. Require one source and lock across all three packages and retain final
   source/ref/submodule/genome/lock closure.
5. Run all automated and manual gates against retained package bytes.
6. Commit evidence only.
7. Create immutable annotated tag `v1.3.0`.
8. Publish the already-qualified ZIPs without rebuilding.
9. Download every published asset into a clean directory.
10. Verify size, SHA-256, ZIP entries, executable metadata, launch, and save/reopen.
11. Record post-publication evidence.
12. Advance `legacy/1.x` to the qualified post-publication checkpoint.
13. Advance `dev/1.x` to the same checkpoint.
14. Only then update the legacy three-line feed on `master`.

After publication, the 1.x branches are effectively frozen under the exception
policy in the branch recovery record.
