## Qualification and promotion gate

Do not fast-forward this checkpoint to `master` or create its tag while
qualification is blocked. Alpha 1 may explicitly retain incomplete future 2.0
features, pending minimum-OS evidence, and Alpha 2 compatibility-laboratory work;
it may not retain a known data-loss path, misleading compatibility claim,
mismatched identity, or unverified package. For this first checkpoint, run the
candidate gate directly on the maintained machine because GitHub only dispatches
a workflow definition present on the default branch. Once qualification passes,
create direct, single-parent child `E` with the exact catalogue-plus-validation
diff, rebuild and validate its full SHA through create-only
`attest/v2.0.0-alpha.1-candidate-<E>` while `dev` remains at `C`, then use
exact-old leases to atomically promote/tag exact `E` to both permanent refs and
consume the transport. The tag bootstraps the workflow onto `master`.

Before that tag is pushed, the owner must configure the
`c3-release-qualification` and `c3-development-compatibility` GitHub
environments, their approval and branch/tag restrictions, and the private
`c3-private-release` runner group with its `c3-legacy-msbuild` worker. Merely
allowing GitHub to auto-create an unprotected environment is not authorized
release evidence.

Then create direct, single-parent alpha child `P`, changing exactly those same
two evidence files. Record promotion `tagged`, publication `unpublished`,
post-verification `not-applicable`, feed promotion `false`, and the exact
annotated tag-object SHA; validate exact `P` through its create-only
`attest/v2.0.0-alpha.1-post-<P>` ref while both
permanent refs remain at `E`, atomically fast-forward it to both `master` and
`dev` with exact-old leases, and consume the temporary ref. Do not create a
GitHub release or promote an alpha feed. Alpha 2 identity and scope begin only
after `P` is on `master`. Minimum-OS
checks may remain explicitly pending here, but no public OS support claim may
rely on them.
