## Shared offline payload verifier

Both setup projects now link `SetupShared/SetupContracts.vb` directly; no setup
DLL is produced. The implementation targets the net40 API floor and enforces:

- DTD/entity-disabled XML parsing and an exact schema/attribute shape;
- exact Alpha/product/lane/source fields ready for caller binding;
- a closed seven-file payload with case-collision rejection;
- canonical root-level names, invariant sizes, and lowercase SHA-256;
- exact extracted file count, length, hash, and reparse-point rejection; and
- local path containment with UNC/device/volume/system/profile-root rejection.

Eight adversarial setup characterization tests pass under the VS2017/net40 test
toolchain, including altered bytes, extra files, traversal, DTD, noncanonical
hashes, and broad install roots. The legacy `frmMain` install button is not yet
wired to this verifier, so the old online path remains classified as open and
must not be executed or distributed.

The shared engine now also writes and strictly rereads `C3.installed.xml`, with
exact product/source/lane/root/mode/transaction/file/registry/shortcut ownership
fields. The state file deliberately does not hash itself. A same-volume staged
file transaction supports clean install, repair, upgrade ordering, downgrade
and lane-change rejection, verified commit, and rollback. Eighteen setup tests
now pass, including preservation of an unknown catalogue, pre-mutation rejection
of an unowned name collision, and injected mid-commit restoration of the exact
prior payload and installed state. The shared removal transaction first verifies
every owned file against `C3.installed.xml`, stages only those owned files on the
same volume, preserves unknown files and a non-empty install directory, removes
the state file, and restores the exact installed state after an injected failure.
Modified owned files fail before mutation. Registry/shortcut mutation, process
handling, self-relocation, and UI activation remain open; the old setup and
uninstall buttons remain prohibited.

## Shared environment preflight

The shared .NET Framework 4.0-compatible preflight captures process and native
architecture, elevation, the Full Framework installation/release, the
operating-system Program Files directory, running C3 processes, and destination
volume free space. It closes the lane mapping, rejects emulation and
cross-architecture installation, enforces the lane's framework floor and an
elevated administrator token, rejects a running C3 instance, and reserves
three times the payload bytes for staging and rollback. It derives the default
product directory from the OS instead of the historical hard-coded x86 path.

Seven focused preflight regressions bring the setup contract suite to 25 passing
tests. Application-manifest elevation metadata and legacy wizard activation are
still open, so this is shared-engine evidence rather than an executable setup
claim.

## Shared registry and shortcut ownership

The installed-state contract now derives one stable uninstall key per lane:
`CompactCassetteCatalogue-1x-x86`, `-x64`, or `-arm64`. The shared registry
service writes a closed Add/Remove Programs value set with quoted executable
paths and explicit state/lane/source ownership markers. It does not advertise
quiet uninstall or Control Panel repair before those entry points exist. An
unowned key collision is refused; removal requires an exact owned value set;
and rollback restores the prior owned values.

The shared shortcut service owns the mandatory common Start Menu link and the
optional common desktop link recorded in `C3.installed.xml`. It validates exact
paths, target, working directory, and description, refuses altered or unowned
links, verifies writes and removals, and restores previously removed links
after an injected failure. Its Windows implementation uses the system shortcut
provider without adding a runtime DLL.

Eight registry/shortcut regressions bring the setup contract suite to 33 passing
tests. The services are not yet composed with the file transaction or activated
by the legacy forms, so no real-machine registry/shortcut qualification is
claimed.
